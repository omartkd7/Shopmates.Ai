1 • شنو هو البرنامج؟

البرنامج هو تعليمات مكتوبة للحاسوب باش يدير خدمة.

Variable • متغير

بحال علبة مسمية كتحتافظ بقيمة. مثلاً stock فيه العدد المتوفر. إلا كانت القيمة 5 وبعنا 2، القيمة الجديدة تولي 3.

Function • دالة

مجموعة تعليمات عندها اسم. كتستقبل معلومات، كتدير خدمة، وقد ترجع نتيجة. checkStock كتقلب على المخزون ديال منتوج.

Object و Array

Object كيجمع خصائص ديال حاجة وحدة: منتوج عندو اسم وثمن ومخزون. Array هي لائحة: مثلاً لائحة المنتجات اللي فالطلب.

Condition • شرط

if كتعني: إلا تحقق الشرط، دير هاد الخدمة. إلا كانت الكمية المطلوبة أكبر من المخزون، نرفض الطلب.

File و Folder

الملف فيه كود أو وثيقة. المجلد كيجمع ملفات مرتبطة. تقسيم المشروع كيساعدنا نلقاو المسؤولية ديال كل جزء.

2 • ثلاث طبقات: بحال محل

تخيل متجر: الواجهة اللي كيشوف الزبون، الموظف اللي كيسير، والدفتر اللي فيه البيانات.

Frontend • الواجهة

هو اللي كيبان فالتليفون: أزرار، صور، فورموليرات، شات. فمشروعك هو mobile باستعمال React Native وExpo. كيجمع اختيار الزبون وكيعرض النتيجة.

Backend • الخادم

هو البرنامج اللي كيستقبل الطلبات، كيتحقق من الهوية والحقوق، كيحسب وكيقرا ويكتب فالقاعدة. فمشروعك هو backend باستعمال Node.js وExpress.

Database • قاعدة البيانات

هي التخزين المنظم والدائم: مستخدمين، منتجات، مخزون، طلبات ورسائل. PostgreSQL هي قاعدة البيانات ديالك.

3 • شنو كيدير كل اسم تقني؟

ما تحفظش الأسماء بوحدها. ربط كل اسم بالخدمة ديالو.

JavaScript و TypeScript

JavaScript لغة البرمجة. TypeScript كتزيد وصف أنواع البيانات وكتكشف أخطاء أثناء التحليل أو البناء. ولكن البيانات اللي جاية من الشبكة خاصها حتى تحقق وقت التشغيل.

Node.js و Express

Node.js كيخلي كود JavaScript يخدم فالخادم. Express كينظم المسارات: مثلاً شنو نديرو ملي يجي طلب ديال المنتجات.

React Native و Expo

React Native كيبني واجهة الموبايل بمكونات. Expo كيوفر أدوات التشغيل والبناء وخدمات للموبايل. Expo Router كيربط الملفات بالشاشات والتنقل.

Zustand و Axios و SecureStore

Zustand كينظم حالة مشتركة فالواجهة، بحال المستخدم الحالي. Axios كيرسل طلبات HTTP. SecureStore كيتستعمل لتخزين حساس فالموبايل؛ ماشي قاعدة بيانات المنتجات.

Sequelize و Zod

Sequelize هو ORM: كيربط كود TypeScript بجداول SQL. Zod كيتأكد أن المدخلات عندها الشكل والقيم المقبولة. الكود الحالي كيستعمل Sequelize؛ الإشارة القديمة لـPrisma فـAGENTS ما كتوافقش هاد التنفيذ.

PostgreSQL و pgvector

PostgreSQL كتحفظ البيانات. pgvector إضافة كتخزن وتقارن المتجهات العددية المستعملة فالبحث الدلالي.

4 • كيفاش كيهضر التليفون مع الخادم؟

API هي واجهة متفق عليها بين برنامجين. HTTP هو البروتوكول المستعمل هنا.

Request • الطلب

فيه العنوان، الطريقة، headers وممكن body. العنوان كيحدد الخدمة. headers فيها معلومات بحال نوع المحتوى ووسيلة إثبات الهوية.

Methods • الطرق

GET للقراية. POST للإرسال أو الإنشاء. PUT/PATCH للتعديل حسب المسار. DELETE للحذف. كل مسار عندو قواعدو.

JSON • شكل البيانات

صيغة نصية كتجمع مفاتيح وقيم. مثال تعليمي ديال منتوج: الاسم والثمن والمخزون. JSON ماشي قاعدة بيانات وماشي لغة ذكاء اصطناعي.

GET /api/products
Authorization: Bearer <access-token>

{"name":"T-shirt","price":120,"stock":5}

Response • الجواب

200 نجاح؛ 201 إنشاء؛ 400 مدخلات غير مقبولة؛ 401 خاص المصادقة أو التوكن غير صالح؛ 403 ما عندكش الحق؛ 404 ما تلقاش المورد؛ 429 طلبات كثيرة؛ 500 خطأ فالخادم. الشكل الدقيق ديال الجواب كيختلف حسب المسار.

5 • كيفاش تقرا سطر كود؟

هاد المثال مبسط للتعليم، ماشي نسخ حرفي من المشروع.
const quantity = 2;
const product = await Product.findOne({
  where: { id: productId, storeId }
});
if (!product) throw new Error("Not found");
if (product.stock < quantity) {
  throw new Error("Insufficient stock");
}

const

كنسمي قيمة باش نرجع نستعملها. quantity هي الكمية المطلوبة.

await

كنستنا نتيجة خدمة غير فورية، بحال القراية من قاعدة البيانات. كتستعمل داخل دالة async. ما كتقصدش نحبس الخادم كامل.

findOne و where

قلب على سجل واحد كيوافق الشروط: معرف المنتوج ومعرف المتجر. هادي طريقة ORM؛ من تحت كاين استعلام SQL.

if و throw

كنختابرو واش المنتوج موجود وواش المخزون كافي. throw كيرسل خطأ لطبقة معالجة الأخطاء. فعملية شراء حقيقية كنحتاجو حتى transaction وlock.

طريقة القراية

بدا بالمدخلات، من بعد الشروط، من بعد الوصول للقاعدة، ومن بعد النتيجة. ما تحاولش تفهم جميع imports قبل ما تعرف الهدف ديال الدالة.

7 • قاعدة البيانات: شنو كتخزن؟

Table جدول، Row سجل، Column خاصية، ID معرف كيخلينا نميزو السجل.

Store / User / Customer

Store هو المتجر. User حساب الدخول والأدوار. Customer بيانات الزبون المستعملة فالطلبات. فالمسارات كاين ربط بالمتجر والبريد؛ User وCustomer ماشي بالضرورة نفس المعرف.

Category كتجمع المنتجات فصنف. Product فيه بيانات المنتوج بحال الثمن والمخزون ومعرف المتجر والصنف. imageUrl رابط صورة، ماشي بالضرورة خدمة رفع وتخزين الصور.

8 • التسجيل والدخول

Authentication كتجاوب: شكون نتا؟ Authorization كتجاوب: شنو مسموح ليك تدير؟

التسجيل

الواجهة كترسل المعلومات. الخادم كيتحقق من الشكل. كيحسب hash لكلمة السر باستعمال bcrypt وكيحفظ الحساب. الحساب العادي كيتسجل بدور CUSTOMER.

Hash ماشي تشفير قابل للعكس

الخادم ما خاصوش يرجع كلمة السر الأصلية من hash. وقت الدخول bcrypt كيقارن الكلمة المدخلة مع hash المخزن بطريقة مناسبة.

الدخول

الخادم كيلقى الحساب وكيقارن كلمة السر. إلا نجح التحقق، كيرجع access token وrefresh token. إلا فشل، ما كيعطيش صلاحية الدخول.

JWT • بطاقة موقعة

Access token كيحمل معلومات بحال userId وstoreId وrole. التوقيع كيخلي الخادم يكشف التلاعب. JWT الموقع ماشي بالضرورة مشفر؛ ما نحطوش فيه أسرار.

Login → Vérification bcrypt → Tokens
Requête → Vérification JWT → Contrôle du rôle → Service

9 • Refresh rotation و logout

Access token للاستعمال اليومي القصير، وrefresh token لتجديد الدخول بلا إعادة كلمة السر كل مرة.

عندما كيسالي access token

الواجهة كتلقى 401، وكتطلب refresh. الخادم كيتحقق من refresh token ومن الصلاحية ديالو، وكيصدر زوج جديد ديال التوكنات.

Rotation • التبديل

Refresh القديم كيتحيد وكيخرج واحد جديد. الهدف هو ما يبقاش نفس السر صالح للتجديد طول الوقت. فالقاعدة كيكون hash بدل القيمة الأصلية.

Axios mutex

إلا عدة طلبات جابو 401 فنفس الوقت، آلية فالعميل كتنسق التجديد باش ما يبداوش كاملين refresh مستقل فنفس اللحظة.

Logout • الخروج

الواجهة كتحيد معلومات الدخول والخادم كيلغي refresh. ولكن access JWT اللي خرج من قبل يقدر يبقى صالح حتى يسالي الوقت ديالو إلا ما كانتش آلية إبطال إضافية.

حد خاص تعرفو

الـrotation الحالية ما خاصناش نوصفوها بضمان مطلق ضد جميع الطلبات المتزامنة. حذف القديم وإصدار الجديد خاصهم مراجعة التزامن والمعاملات باش يكون الضمان أقوى.

10 • Multi-tenant: كل متجر وبياناتو

Tenant هنا هو متجر. نفس التطبيق يقدر يخدم أكثر من متجر مع عزل البيانات.

storeId

معرف المتجر كيدخل فشروط الوصول للبيانات التابعة ليه. فالمسارات المحمية كيجي من JWT المتحقق منو فالخادم، ماشي من اختيار الزبون فالطلب.

مثال

متجر A عندو منتوج، ومتجر B عندو منتوج آخر. إلا مستخدم A عرف ID ديال منتوج B، الخادم خاصو يبحث بالـID وstoreId معاً. معرفة المعرف ما كتمنحش الحق.

الزبون داخل نفس المتجر

حتى داخل A، ما خاصش زبون يشوف طلب زبون آخر. كنحتاجو التحقق من مالك الطلب زيادة على المتجر.

الدور ADMIN

إظهار شاشة الإدارة غير للمسؤول مفيد فالواجهة. لكن الحماية الحقيقية كتكون حتى فالخادم قبل القراءة أو التعديل.

تفصيل فنسخة الديمو

التسجيل والدخول كيرتبطو بمتجر الديمو المحدد فالخادم. بعض قراءات الكاتالوغ العامة كتستعمل متجر الديمو كذلك. ما تقولش إن كل request عامة كتحتاج JWT، ولا إن التسجيل كيدير اختيار حر للمتجر.

11 • الكاتالوغ والإدارة

CRUD: Create إنشاء، Read قراية، Update تعديل، Delete حذف.

رحلة عرض المنتجات

الشاشة كتطلب المنتجات. الخادم كيتحقق من الفلاتر والمتجر. القاعدة كترجع النتائج. الواجهة كتبيّن اللائحة، التحميل، الفراغ أو الخطأ.

Pagination • تقسيم اللائحة

ما كنجيبووش جميع المنتجات دفعة وحدة. كنطلبو جزء، ومن بعد جزء آخر. هادشي كيخفف الاستجابة والذاكرة.

المسؤول كيعدل

ADMIN يقدر يدير عمليات الكاتالوغ المسموحة: منتجات، أصناف، ثمن ومخزون. الخادم كيتحقق من الدور والمدخلات. حذف منتوج خاصو واجهة تأكيد ومعالجة القيود المرتبطة بالطلبات.

Validation • التحقق

14 • RAG: نجبدو المعرفة قبل الجواب

RAG = Retrieval Augmented Generation. بالبساطة: نقلبو على معلومة مناسبة، ونمدوها للنموذج باش يجاوب منها.

المشكل

الزبون كيسول على مدة التوصيل. النموذج ما خاصوش يخترع سياسة المتجر. خاصو يعتمد على وثيقة حقيقية مرفوعة من المسؤول.

مرحلتان

Ingestion هي إدخال الوثائق وتحضيرها للبحث. Retrieval هي البحث على المقاطع المناسبة وقت السؤال. Generation هي صياغة الجواب من السياق.

رفع الوثيقة

المسؤول كيرفع ملف md أو txt حتى 2 Mo عبر POST /api/documents. الخادم كيحضّر المقاطع والمتجهات ويحفظها. واجهة الإدارة كتخدم لائحة الوثائق والحذف وحالة المعالجة؛ إلا فشل الرفع ما نفترضوش أن المعرفة تزادت.

مثال تعليمي

وثيقة كتقول: التوصيل للمدينة بين يومين وثلاثة. السؤال: شحال حتى توصلني؟ كنرجعو المقطع المناسب ونطلبو جواب مبني عليه مع المصدر.

Document → Chunks → Embeddings → pgvector
Question → Embedding → Recherche → Contexte → Réponse + source

23 • Docker و migrations و seed

الهدف هو تجهيز تشغيل متشابه فالأجهزة والخادم.

Image وصف مبني فيه التطبيق وما يحتاجو. Container عملية تشغيل معزولة نسبياً انطلقت من image. Volume كيحتافظ ببيانات القاعدة خارج عمر container.

Multi-stage Dockerfile

مرحلة build كتجهز الكود، ومرحلة runtime كتحتافظ بما يلزم للتشغيل. مستخدم non-root كيقلل الصلاحيات داخل الحاوية.

Migration

تغيير منظم فبنية القاعدة: جدول جديد أو عمود أو index. ماشي نسخة احتياطية. pgvector SQL كيمكن الامتداد والبنية اللازمة للبحث المتجهي حسب السكريبتات.

Seed
